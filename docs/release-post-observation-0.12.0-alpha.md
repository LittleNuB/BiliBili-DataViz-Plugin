## 重点观察路径

### 安装、Manifest、MV3 Service Worker

- 检查用户是否选择了正确的解压扩展根目录。
- 记录 manifest 加载失败、host 权限拒绝、企业策略拦截或 MV3 Service Worker 启动错误。
- 若仅是安装说明不清，优先修正文档或公告，不要替换已发布 zip。

### Popup、Dashboard 与设置页

- 记录空白页、首屏 crash、路由打不开、重复打开异常或只在旧本地数据下触发的问题。
- 区分是 Popup 独立问题、Dashboard 独立问题，还是 Service Worker/存储初始化导致的连带失败。
- 重点观察设置页是否让用户理解：AI 是可选增强，配置保存在本地，危险本地数据操作需要二次确认。

### Smart Favorites 问答与同步边界

- 观察收藏同步诊断是否能解释“为什么只覆盖当前已同步收藏”。
- 本地结果必须保留引用视频、命中原因和同步覆盖提示。
- AI 可用时只做本地结果组织；AI 不可用或输出被拒绝时仍要保留本地检索结果，不得返回无来源结论。

### 当前视频 Agent 与时间点安全

- 观察当前视频上下文能否稳定命中活动 B 站视频页，而不是退化到扩展页上下文。
- 当前视频回答只使用当前视频证据；没有字幕正文时必须保持有限结论。
- 时间点跳转必须先预览、再确认、可返回；任何无确认 seek 都按 must-fix 或 blocker 评估。
- 真实页面拿不到字幕正文时，要确认提示能解释访问限制或字幕源不可用，而不是伪装成完整理解。

### 当前视频相关收藏

- 相关收藏必须保持为独立分区，不作为当前视频回答证据。
- 同步不完整时，文案必须限定为当前已同步收藏。
- 打开相关收藏只能跳转到 B 站视频页，不写回收藏夹或改变 B 站数据。

### 视频盲盒候选来源

- 随机探索和换口味应明确来自真实 B 站候选源。
- 冷门收藏应明确是本地收藏回访。
- 本地兴趣回顾只基于本地观看历史做回看提示，不读取关注新投稿，也不替代 Dynamic Bill。
- 候选源不可用时，要显示原因和重试入口，不用本地库存冒充外部探索。

### Dynamic Bill 兴趣再平衡

- Dynamic Bill 仍然服务于兴趣再平衡，不是推荐排序、点击率优化或动态流替代品。
- “少提醒这个 UP / 少提醒这个主题”类反馈必须被理解为本地抑制信号，而不是写回 B 站关系。
- AI 不可用时，本地证据与状态说明仍需可读。

### 隐私边界误解或用户反馈

- 重点收集“是否上传完整本地数据”“是否会自动改动 B 站关系”“是否会读取本地登录凭据或密钥文件”这几类误解。
- 若只是理解偏差，优先补充说明；若发现真实越界行为，立即升级为 blocker。

## 失败分级

### Blocker

满足任一条件即视为 blocker：

- 发布 zip 无法下载、SHA-256 与公开记录不一致，或 zip 内容不是可加载扩展目录。
- 主流 Chrome/Edge 稳定版普遍无法安装，或 manifest / MV3 service worker 失败导致扩展无法启动。
- Popup、Dashboard 或设置页首屏普遍 crash，导致核心路径不可进入。
- 当前视频 Agent、Smart Favorites、视频盲盒或 Dynamic Bill 在正常支持环境下高频失效，且没有可理解的本地结果。
- 当前视频跳转绕过预览/确认，直接改变播放位置。
- 发现会写回 B 站关注、收藏、评论、点赞、投币或播放状态的行为。
- 发现上传完整历史、完整收藏、完整关注、完整反馈，或读取本地敏感文件的真实越界行为。

### Must-fix

必须在下一个 alpha 修补，但不一定要求立即撤下当前 prerelease：

- 安装说明、权限说明或隐私说明不清，导致多名用户重复误操作。
- 某个页面或模块在特定旧数据环境下 crash，但存在稳定绕开方式，其他核心路径仍可用。
- Smart Favorites、当前视频 Agent、视频盲盒或 Dynamic Bill 的本地结果能工作，但说明文案明显误导。
- 相关收藏边界、同步覆盖范围或视频盲盒候选来源让用户误以为覆盖范围更大。
- 当前视频时间点安全逻辑可用，但预览、确认、返回的提示不够清楚。
- 构建仍出现已知 Vite warning，但不影响安装、加载或核心功能。

### Follow-up

进入普通后续排期：

- 视频盲盒候选质量、原因解释或重试体验优化。
- 当前视频查询改写、证据片段排序、相关收藏召回质量优化。
- Smart Favorites 知识库后续实现切片。
- 更细的同步进度、失败重试、诊断导出或说明增强。
- 文案微调、FAQ、帮助文档、问卷或反馈入口优化。
- 构建体积和 chunk 切分优化。

## 回滚与补丁策略

### 总原则

- 不静默覆盖已经公开发布并可能已被下载的 `bili-bill-0.12.0-alpha.zip`。
- 优先保留公开 tag `v0.12.0-alpha` 作为历史指针，不移动、不替换、不强推覆盖。
- Chrome Web Store 尚未发布，本次不涉及商店回滚或商店审查说明。

### Blocker 处置

1. 先确认问题可复现，并记录浏览器版本、OS、扩展 ID、release zip SHA-256、Console 错误、Service Worker 错误、IndexedDB 版本和最小复现步骤。
2. 立即在 issue 与 release 沟通中标明当前 prerelease 有风险。
3. 由维护者决定：
   - 撤下当前 prerelease 的推荐状态，或在 prerelease 说明中显式标记 blocker。
   - 从已发布基线派生修复，并发布 `0.12.0-alpha.1` 或新的 alpha tag。
4. 不要通过静默替换 zip 假装问题从未发生。

### Artifact replacement 规则

只有在极少数发布物层面的事故下，才讨论 replacement：

- 上传损坏、文件名错误、release 页面缺失文件，或公开记录的 SHA-256 与下载文件不一致。

若维护者明确决定替换 asset，则必须：

- 重新生成 zip 与新的 SHA-256。
- 在 release notes 中透明说明替换时间、原因、影响范围和新校验值。
- 保留用户能区分旧 artifact 与新 artifact 的说明。

即便满足 replacement 条件，仍然优先选择发布 `0.12.0-alpha.1` 或新的 tag，而不是复写既有公开下载物。

### Tag 与补丁版本策略

- 不移动 `v0.12.0-alpha`，不 force-move public tag。
- 修复版优先使用 `v0.12.0-alpha.1` 或新的明确 tag。
- 若只是文档说明补充，不需要改 tag 或替换 asset。

## 本地数据与诊断说明

- 本版本继续依赖浏览器本地 `IndexedDB` 与 `chrome.storage.local` 保存历史、偏好、Smart Favorites、当前视频缓存、视频盲盒状态和 Dynamic Bill 本地状态。
- 不要默认建议用户清空本地数据库、删除扩展存储或重装浏览器用户目录。
- 只有在诊断已经确认是本地旧数据损坏、迁移失败或不可恢复缓存导致的问题时，清库才作为最后手段。
- 即使进入诊断，也应先收集错误信息、数据库版本、可复现路径和受影响页面，再决定是否需要让用户执行清理。
- 任何诊断与回滚流程都不应要求用户提供本地登录凭据、浏览器用户目录、B 站登录文件、密钥文件或其他本地敏感文件。

```text

如果仍然失败，请提供浏览器版本、操作系统、扩展报错截图和最小复现步骤。请不要提供本地登录凭据、浏览器用户目录或密钥文件。
```

```text
0.12.0-alpha 的 AI 能力是可选增强，不是核心可用性的前提。即使 AI 未配置、被禁用或请求失败，Bili-Bill 仍应保留本地结果。

如果你看到的是空白或无来源结论，请反馈具体页面、当时是否启用 AI、报错信息和截图，我们会优先确认本地结果是否异常。
```

```text
当前视频跳转必须先预览、再确认，并允许返回原位置。如果你遇到没有确认就改变播放位置的情况，请反馈视频页面、操作步骤、预览前后的时间点和浏览器版本。

请不要提供本地登录凭据或浏览器用户目录；我们只需要页面可见信息和复现步骤。
```

```text
它也不会写回 B 站关注/收藏关系。如果你看到让你怀疑越界的行为，请直接反馈页面、时间点和截图，我们会按 blocker 级别核查。
```

## 后续 Triage 流程

1. 每条反馈先记录来源、浏览器、OS、安装方式、是否启用 AI、是否存在旧本地数据、release zip SHA-256 和最小复现步骤。
2. 先按类别归档：
   - 安装/manifest/service worker
   - Popup/Dashboard/设置页启动
   - Smart Favorites 同步完整性与问答
   - 当前视频 Agent、相关收藏和时间点跳转
   - 视频盲盒候选来源
   - Dynamic Bill 兴趣再平衡
   - 隐私边界或用户误解
3. 先判断是否命中 blocker；命中则单开高优先级 issue，并在标题中直接写影响面。
4. 未命中 blocker 但需要下一个 alpha 修补的，拆成 must-fix issue；标题应具体描述用户可见症状，不写模糊的“优化体验”。
5. 其余进入 follow-up issue，记录样本、预期行为和建议方向。
6. 每个拆出的 issue 至少包含：
   - 观察窗口与首次发现时间
   - 影响版本与 release SHA-256
   - 复现步骤
   - 实际结果与期望结果
   - 是否涉及旧本地数据
   - 是否触及隐私或写回边界
   - 建议分级：blocker / must-fix / follow-up
