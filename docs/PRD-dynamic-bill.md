# Bili-Bill 动态账单 PRD

## 1. 背景

Bili-Bill 是面向 B 站高频用户的个人内容账单工具。现有能力偏向“消费后”：观看历史归档、消费分析、智能收藏夹整理。动态账单补齐“消费前”场景：在用户打开关注动态或视频前，帮助用户看见被近期口味覆盖的长期关注和旧兴趣。

B 站已有动态推荐和个性化排序能力，会强化用户最近最可能点击的内容。动态账单不做另一套“猜你喜欢”，而是围绕兴趣再平衡，提醒用户有哪些值得重新考虑的已关注视频投稿。

## 2. 产品定位

**动态账单** 是用户消费已关注账号的视频投稿动态前，由 AI 提供的消费引导视图。

它的目标不是提高点击率，而是帮助用户回答：

- 我是不是忘了某些关注很久的 UP？
- 我最近是不是只看某一类内容？
- 过去长期喜欢但近期没看的主题里，有没有新投稿？
- 哪些关注关系已经变成旧账，可能需要回访或清理？

## 3. 目标用户

- 关注 UP 较多，原生动态页容易刷不过来的 B 站用户。
- 观看兴趣阶段性偏移明显，希望恢复内容多样性的用户。
- 希望理解自己长期关注关系，而不是只被近期行为驱动的用户。
- 已使用 Bili-Bill 观看历史和智能收藏夹能力，希望进一步管理消费前决策的用户。

### 3.1 核心用户场景

- 作为一个关注很多 UP 的用户，我想在打开 B 站动态前先看到被近期口味盖住的新投稿，避免只消费最近算法持续强化的内容。
- 作为一个长期使用 Bili-Bill 的用户，我想知道某个账单项为什么出现，而不是只看到一个不透明推荐结果。
- 作为一个已经不确定某些关注是否仍有价值的用户，我想先通过低压力提醒回访或处理，而不是被产品直接推动取关。
- 作为一个重视本地数据边界的用户，我想确认动态账单只用必要的本地事实和入选视频元数据生成解释，不上传完整历史或完整关注列表。

## 4. 第一版范围

第一版只覆盖 **已关注 UP 的视频投稿动态**。

包含：

- Dashboard 一级入口：动态账单。
- 三个账单栏目：久违更新、换换口味、被淹没的关注。
- 账单项状态：未打开、已打开、已消费、已处理。
- 本地负反馈：少提醒这个 UP、少提醒这个主题。
- 取关提示：提示用户去 B 站检查关注关系，但不直接取关。
- AI 摘要和解释。
- Bili-Bill 品牌外壳刷新，保证新旧页面视觉一致。

不包含：

- 图文动态、转发动态、直播提醒、专栏、番剧追番提醒。
- 直接改写 B 站动态页排序。
- 系统通知。
- 插件内一键取关、自动取关、批量取关。
- 上传完整观看历史或完整关注列表给 AI。
- 用 AI 决定入选规则或排序。
- 商业推广、创作者扶持位、付费分发或“帮 UP 主找回流量”。
- 非关注内容推荐、跨平台内容推荐、替代 B 站推荐流或动态页。
- 以提升总点击率、观看时长或留存为第一优化目标。
- 对旧 Dashboard 分析模块做深度信息架构重构。

### 4.1 v1 MVP 边界

v1 的最小可交付版本必须完成一条闭环：同步已关注视频投稿，基于本地规则生成三类兴趣再平衡账单项，展示可解释证据，允许用户打开、处理和反馈，并在 AI 不可用时仍可用。

必须包含：

- 数据池：最近 7 天已关注 UP 的视频投稿动态。
- 分析窗口：长期观看窗口 180 天、近期观看窗口 30 天；本地历史不足时明确提示。
- 账单栏目：久违更新、换换口味、被淹没的关注，三者必须有不同入选理由。
- 账单项：至少包含 UP 主、新投稿视频、本地证据事实、状态、打开入口、处理入口、负反馈入口。
- 状态：未打开、已打开、已消费、已处理，默认视图优先展示未打开和已打开。
- AI：只作为摘要和解释增强；AI Key 缺失、生成失败或用户未启用 AI 时，仍展示本地证据版账单。
- 品牌外壳：同版本完成 Bili-Bill shell、一级导航和旧页面外壳统一。

可以延后：

- 虚拟滚动、复杂分页、跨设备同步、多账号切换。
- AI 自动聚类主题、长期趋势洞察、个性化阈值配置面板。
- 系统通知、浏览器角标策略、原生 B 站动态页注入。
- 负反馈的复杂原因树；v1 只需要 creator/topic 两个范围。

### 4.2 待验证假设

- H1：用户能把动态账单理解为“兴趣再平衡”，而不是又一个猜你喜欢推荐流。
- H2：长期-近期落差、久未观看 UP、已关注时间这些信号能产生足够多且不显得随机的账单项。
- H3：关注列表和动态视频投稿接口足够稳定；如果已关注时间不可用，降级解释仍然可信。
- H4：本地证据事实足以支撑用户信任，AI 解释只是锦上添花而不是可用性的前提。
- H5：负反馈和取关提示的文案不会让用户觉得 Bili-Bill 在替他们审判关注关系。
- H6：品牌 shell 刷新足以避免新旧页面割裂，且不会把 v1 拖成旧 Dashboard 重构项目。

## 5. 核心差异化

| 维度 | B 站动态/推荐 | Bili-Bill 动态账单 |
| --- | --- | --- |
| 核心目标 | 让用户更快点开近期可能爱看的内容 | 帮用户恢复更宽的关注消费结构 |
| 主要信号 | 近期行为、互动、兴趣偏好 | 长期历史、久未观看、分区失衡、已关注时间 |
| 体验倾向 | 越看越像最近的自己 | 提醒你过去也关心过什么 |
| 内容池 | 平台推荐和关注流 | 第一版只看已关注 UP 的视频投稿 |
| AI 作用 | 不透明排序的一部分 | 摘要和解释“为什么值得重新考虑” |
| 用户感受 | 猜你喜欢 | 你是不是忘了这些关注 |

## 6. 账单栏目

### 6.1 久违更新

用于展示过去有明显观看正反馈、但近期冷却的 UP 的新视频。

入选方向：

- UP 在长期观看窗口内有正反馈。
- UP 在近期观看窗口内明显冷却。
- UP 在动态内容窗口内发布了视频投稿。
- 已关注时间可提高解释权重和排序权重，但不单独决定入选。
- 排除用户近期已经看过的同一视频。

典型解释：

> 你过去 180 天看过这个 UP 12 次，但最近 30 天没有打开过；这期新投稿可以补回这条历史兴趣线。

### 6.2 换换口味

用于展示长期喜欢、但近期消费占比明显下降的分区或标签里的新视频。

入选方向：

- 分区或标签在长期观看窗口中是稳定兴趣。
- 同一分区或标签在近期观看窗口中明显下降。
- 动态内容窗口内有关注 UP 发布相关视频。
- 第一版按 B 站分区、标签和本地归一化类目判断，不使用 AI 自创主题簇。

典型解释：

> 你的长期兴趣里有游戏美术和视觉设计，但最近消费集中在数码评测；这条可以作为今天的口味切换。

### 6.3 被淹没的关注

用于展示关注时间较长、但近期几乎没有消费的 UP 的新视频。

入选方向：

- UP 有稳定关注关系，尤其是已关注时间较长。
- 近期观看记录中该 UP 缺席或近乎缺席。
- 不要求历史观看正反馈很强，这一点与久违更新区分。
- 重复负反馈后可触发取关提示。

典型解释：

> 这个 UP 不一定是高频观看对象，但你保留关注 5 年。它代表的是长期品味线索，而不是最近算法推断出的点击概率。

## 7. 数据窗口

默认窗口：

- 长期观看窗口：过去 180 天；如果本地历史不足 180 天，则使用全部可用历史。
- 近期观看窗口：过去 30 天。
- 动态内容窗口：最近 7 天关注视频投稿。
- 关注关系窗口：使用可获取的已关注时间，不截断；若拿不到关注时间，则展示“已关注，关注时长未知”。

历史保留策略：

- 新安装默认历史保留期调整为 180 天。
- 老用户不强制覆盖已有设置。
- 若当前保留期低于 180 天，动态账单页面应提示“长期品味判断会偏短”。

## 8. 账单项模型

账单项不等于单个视频卡片。它可以是：

- 以 UP 主为中心，附带新视频和历史代表视频。
- 以新视频为中心，附带 UP 主上下文和历史代表视频。

账单项应包含：

- 账单栏目。
- 账单状态。
- UP 主信息。
- 关注时长和关注日期，若可用。
- 新投稿视频。
- 本地历史代表视频，最多 3 个。
- 证据事实。
- AI 摘要与解释。
- 负反馈和处理操作。

历史代表视频只从本地观看历史中选择，不远程拉取 UP 全部公开视频。

## 9. 状态模型

- **未打开**：用户尚未从动态账单打开新视频。
- **已打开**：用户从动态账单打开过新视频，但 Bili-Bill 尚未确认有效观看。
- **已消费**：通过观看历史或播放器事件确认用户有效观看。
- **已处理**：用户手动处理或忽略该账单项，不要求确认观看。

默认视图以未打开和已打开项为主，已消费和已处理项可通过筛选查看。

## 10. AI 角色

AI 不决定入选，也不决定排序。第一版由本地规则决定账单项是否入选，AI 负责：

- 生成一句话视频摘要。
- 生成为什么进入该栏目的解释。
- 生成建议观看角度。
- 生成少量关键词，供搜索和后续聚合使用。

AI 输出建议字段：

- `summary`
- `reason`
- `viewingAngle`
- `keywords`
- `confidence`

`confidence` 仅表示 AI 对摘要/解释质量的自评，不参与入选规则。

## 11. AI 数据最小化

允许上传给 AI：

- 入选视频的标题、简介、UP 名称、分区、标签、时长、发布时间。
- 入选栏目名称。
- 本地规则生成的紧凑证据事实。
- 少量聚合统计，例如“过去 180 天看过 12 次，最近 30 天 0 次”。

不上传：

- 完整观看历史。
- 完整关注列表。
- Cookie、用户 mid、个人资料。
- 未入选动态的大批量原始数据。
- 弹幕、评论、画面内容。

## 12. 负反馈与取关提示

第一版提供本地负反馈：

- 少提醒这个 UP。
- 少提醒这个主题。

负反馈只影响 Bili-Bill 本地规则，不上传、不训练外部模型、不写回 B 站。

负反馈确认文案应强调“本地”和“可逆的提醒强度”，避免让用户以为插件会修改 B 站关系：

> 已记录。Bili-Bill 会在本地降低类似账单项出现频率，不会影响你在 B 站的关注。

当同一 UP 被多次负反馈后，动态账单可以显示取关提示：

> 你已经多次选择少提醒这个 UP。要去 B 站检查是否还需要继续关注吗？

取关提示只提供“打开 UP 主页”和“暂不处理”，不提供插件内取关。

## 13. 同步与生成

同步策略：

- 动态视频元数据同步与 AI 生成分离。
- 用户打开动态账单时可手动刷新动态。
- 动态元数据可以较频繁同步。
- AI 账单生成默认低频，避免消耗用户 API Key 和触发 MV3 长任务风险。
- AI 生成采用短批次，类似智能收藏夹索引策略。

第一版不做系统通知，只在 Bili-Bill 内部显示动态账单入口和数量。

## 14. UI 结构

参考原型：`../dynamic-bill-prototype`。

第一版 UI 需求：

- Dashboard 采用 Bili-Bill 品牌外壳。
- 侧边栏导航，动态账单为一级入口。
- 顶部显示本次账单时间、历史窗口、动态窗口、可用历史状态。
- 兴趣再平衡摘要区展示近期集中度、长期兴趣缺口、老关注唤回等聚合信息。
- 主体采用三栏账单板：久违更新、换换口味、被淹没的关注。
- 右侧或下方详情面板展示选中账单项。
- 状态筛选必须覆盖未打开、已打开、已消费、已处理；不得把未打开文案写成“未消费”。
- 移动端降级为单列列表，详情随内容向下展开。

账单项卡片应展示：

- UP 主。
- 关注时长。
- 新视频。
- 证据事实。
- AI 解释摘要。
- 本地历史代表视频。
- 打开新视频、打开 UP 主页、标记已处理、负反馈操作。

原型中应固化为需求的结构：

- Bili-Bill shell、侧边栏一级导航、动态账单选中态。
- 顶部数据状态区和状态筛选。
- 兴趣再平衡摘要区，但具体指标名称和数量可按真实数据调整。
- 三个账单栏目及每栏数量、空状态。
- 卡片 + 详情面板的主从结构。
- 证据事实、AI 解释、本地历史代表视频三段详情。
- 打开新视频、打开 UP 主页、标记已处理、负反馈、取关提示的操作入口。
- 窄屏单列展示。

原型中仅作为设计参考，不作为 v1 硬性需求：

- 精确配色、渐变、阴影、间距和品牌图标样式。
- “今天建议先看一条不同口味”的轨道可视化。
- mock 数据中的具体 UP、视频、指标数值和 toast 文案。
- 详情面板必须固定在右侧；真实实现可在窄屏或中等屏下放到下方。
- 原型缺失的已消费筛选和负反馈入口不得视为 v1 可省略。

## 15. 旧 UI 一致性

动态账单版本必须包含 Bili-Bill 品牌外壳刷新，避免新页面和旧 Dashboard 割裂。

同版本必须做：

- 插件名和主标题改为 Bili-Bill。
- Dashboard 默认首页 v1 继续保留现有“总览”，动态账单作为一级入口而不是默认首页。
- Dashboard 导航与动态账单原型保持一致或接近。
- 颜色、卡片、按钮、状态标签、字体层级统一。
- 旧页面至少完成外壳统一。
- 旧分析模块只做必要的品牌下归位和入口命名，不改变核心指标口径和内部信息架构。

后续版本再做：

- 旧页面信息架构深度重构。
- 图表体系重新设计。
- Popup 完整 redesign。
- 各分析模块指标命名体系重构。

## 16. 成功标准

v1 不以总点击率、观看时长或推荐命中率作为成功指标。动态账单的核心成功是：用户理解它为什么提醒、愿意尝试非近期高频内容，并能通过反馈降低错误提醒。

产品验证指标：

- 理解：可用性测试中，多数用户能说出动态账单不是普通推荐流，而是关注内容的兴趣再平衡视图。
- 可解释：用户阅读账单项后，能复述该项进入栏目的至少一个本地证据事实。
- 行动：有未打开账单项的会话中，用户愿意打开至少一条非近期高频兴趣视频，或明确标记已处理。
- 反馈：用户能找到并使用 creator/topic 两类负反馈；后续生成中同类错误提醒减少。
- 边界感：用户看到取关提示后不认为 Bili-Bill 会替自己取关或修改 B 站关注关系。
- 信任：AI 失败或未启用时，用户仍能根据本地证据理解账单项。

工程验收指标：

- 动态账单页面可加载并展示三个栏目。
- 本地规则可生成账单项。
- AI 解释失败时页面仍可展示本地证据。
- 打开视频、打开 UP 主页、标记已处理、负反馈可用。
- 已打开和已消费状态能区分。
- 老用户历史不足 180 天时有明确提示。
- 不上传完整历史和完整关注列表。

建议 alpha 观察口径：

- `bill_items_generated_count`：每次生成的账单项数量，按栏目统计。
- `non_recent_opened_count`：从动态账单打开的非近期高频兴趣视频数量。
- `processed_count`：用户主动标记已处理的账单项数量。
- `negative_feedback_count`：creator/topic 负反馈数量及重复命中情况。
- `explanation_fallback_rate`：AI 失败或未启用时本地证据 fallback 的占比。
- `privacy_payload_audit_passed`：AI 请求不含完整历史、完整关注列表、Cookie、用户 mid 或个人资料。

## 17. 风险

- B 站动态和关注关系接口稳定性未确认，需要技术 spike。
- 已关注时间字段可能不可用或语义不稳定，需要降级。
- 真实数据量大时，三栏列表可能需要折叠、分页或虚拟滚动。
- AI 解释过长或过自信会降低可信度，需要长度控制。
- 旧 UI 外壳刷新可能扩大版本范围，需要避免深度重构旧页面。

## 18. PM 审核结论

当前 PRD 的产品方向、核心差异化和关键技术边界已经稳定，可以作为 v1 开发输入。相比交接时的版本，本轮补齐了以下可交付缺口：

- 增加核心用户场景，避免文档只描述功能而缺少用户任务。
- 明确 v1 MVP 闭环，把“动态同步、规则账单、本地证据、AI fallback、状态与反馈”列为最小交付。
- 扩展非目标，明确不做商业推广、创作者扶持、推荐流替代和旧 Dashboard 深度重构。
- 增加待验证假设，区分已决策事项和仍需 spike/alpha 验证的风险。
- 明确成功指标口径，不再把“页面存在”或“点击率提升”当作核心成功。
- 将已通过原型拆分为需求结构和设计参考，避免开发误把 mock 文案、视觉细节或原型缺口当成产品要求。

仍需在开发前后关闭：

- 动态 feed API 和关注关系 API 的可用性 spike。
- 已关注时间不可用时，“被淹没的关注”是否仍能产生可信账单项。
- 小样本用户是否理解“兴趣再平衡”而非“猜你喜欢”。
- 负反馈与取关提示文案是否足够低压力。
- 品牌 shell 刷新是否能在不重构旧分析页的前提下保持一致。
